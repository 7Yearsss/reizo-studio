# Provider resolution and usage ledger

`providerResolver.ts` owns common validation and effective model selection. Image and LLM use existing Settings presets; audio uses the managed registry; video accepts managed video IDs and legacy `mock`/`fal`/`kling` driver settings. User configuration files are not migrated or rewritten by this resolver. Implicit image key fallback remains compatible; an explicitly selected missing provider never silently changes to another paid account. An unconfigured installation retains local mock video behavior. A configured managed default remains subject to the existing generation spend gate.

Driver protocols stay distinct. Audio model hooks describe the model actually sent. Kling retains its native API and saved query mode. FAL keeps submit/status/result queue behavior and exact persisted query URLs. An explicit `owner/model` ID selects a model endpoint on the validated configured origin; without one, existing complete endpoints and old display labels retain their legacy behavior. Public provider catalogs and usage records contain no credentials. Submitted model and supplier-reported model versions are shown separately.

## Three independent data sources

- **Reported usage:** only explicit finite counters returned by the provider/SDK. Input, output, cached and cache-write token fields are separate; input totals overlap their component metrics and must not be summed as another billable unit. Missing data remains unknown.
- **Observed output:** counts of nonempty image results and locally probed composition duration. These are observations, not provider billing statements. A configured per-output estimate can use them, while preserving their source label.
- **Bill evidence:** an explicitly entered amount, currency, source and charge-line reference. This is locally attached evidence; it is not an automated verification against the provider's billing account.

OpenAI Chat Completions reports request totals in its final usage chunk; interruption can omit that chunk. Responses includes usage on terminal responses. The implementation preserves final, self-consistent counters supplied on `response.incomplete` or `response.failed` despite unsuccessful business output: quantities retain `provider_reported` basis with a `partial` state and distinct `reportOutcomes`. A generic SSE error, network abort or missing final report remains unknown. Output token counts cover more than visible text, and cache writes have their own counters. The transport observer preserves the consumed bytes, backpressure, cancellation and quota lifetime, keeps only the latest usage candidate, and persists it after terminal markers plus normal EOF. Malformed, contradictory or oversized accounting frames remain unknown; response text/prompts are never stored in ledger reports. Null/non-object frames cannot break the consumer's original stream. These mappings follow the [official Chat Completions reference](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create) and [official prompt caching guide](https://developers.openai.com/api/docs/guides/prompt-caching); the [official reasoning guide](https://developers.openai.com/api/docs/guides/reasoning) explains why incomplete output can still incur input/reasoning usage. FAL selection uses its [documented model IDs](https://fal.ai/docs/examples/video-generation/generate-videos-from-image).

## Pricing and reconciliation

No real vendor prices are preloaded or guessed. A price snapshot requires an explicit provider, model, category, currency, source, effective time and rate/unit bases. Snapshot rows are immutable and are frozen when an execution first submits. New prices do not rewrite old executions. Estimation requires every recorded underlying report to contain each configured priced metric; otherwise its estimate remains unknown. A snapshot may cover only selected charges, so the calculated estimate is not a complete invoice. Total-token pricing cannot be combined with input/output component pricing; total input pricing cannot be combined with cached/uncached/cache-write component pricing. Currency totals remain separate; there is no implicit FX conversion. Quantities are bounded by the safe integer range, and amounts/rates by 1e12. Aggregates exceeding those limits are omitted with explicit summary warnings, rather than represented as zero or JSON null. Tiny nonzero estimates are retained.

Bills remain separate from estimates. One charge line can attach once to one execution; source plus reference must identify the individual charge line, not an entire invoice reused for several jobs. Stable IDs safely replay identical price/bill submissions, while changed identity reuse is rejected. A recorded bill is marked `bill_recorded`, `amount_differs` or `currency_mismatch`; absent bills remain `unreconciled`. A manually entered bill is never labeled supplier-verified. Amount comparison applies only when currencies match.

`executionCount` counts all ledger contexts: one context per media job, local export and main-LLM HTTP attempt. `localCount` counts reliable `category=local` plus `providerId=local` identities, and `supplierExecutionCount` counts the remaining contexts. Known/partial/observed/unknown/unreconciled counters and metric/estimate/bill totals cover only supplier executions, so local export does not masquerade as unknown supplier usage or a missing supplier invoice. Local records remain available with their actual identity; no artificial zero cost is assigned. `reportCount` tracks underlying observations. Execution and report counts are not money, and currency totals remain separate.

## Storage and API

SQLite migration `0011_usage_ledger` creates pricing snapshots, execution records, individual report identities and bill evidence. Existing submitted jobs receive unknown legacy rows; no historical usage or prices are fabricated. Job submission freezes actual provider/model, including driver-selected models. Report replacement and aggregate recomputation use one SQLite savepoint, so cumulative stream frames and replay do not multiply counters.

| Request | Purpose |
| --- | --- |
| `GET /api/usage/summary` | Global known/unknown counts, metric totals, separate currency estimate/bill totals. |
| `GET /api/usage/records?jobId=&limit=&cursor=` | Stable cursor pagination, optionally restricted to one job. |
| `GET /api/usage/pricing` | Explicit snapshots with source and effective dates. |
| `POST /api/usage/pricing` | Append a price snapshot; stable IDs replay identical input. |
| `POST /api/usage/bills` | Attach one explicit bill evidence record to an execution. |

The Settings usage/cost section and job details use these APIs through the normal loopback/origin guard. Capture covers app-backed image/audio/video/agent jobs, main LLM HTTP attempts (including same-model background work), prompt refinement and local composition observations. Drivers without reported usage remain unknown. The legacy image-tool path without a canvas/SQLite repository cannot persist accounting. Future external bill imports, vendor account reconciliation, service-tier/tax/discount handling and additional provider-specific metering need explicit adapters and evidence; no real paid calls were used for development validation.
